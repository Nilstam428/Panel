# WhatsApp Admin Notification Bot — TODO

## Goal

Build a manually controlled WhatsApp notification system:

```text
Admin Panel
    ↓
FastAPI backend
    ↓
Validate admin input
    ↓
Select approved WhatsApp template
    ↓
Render template variables
    ↓
Meta WhatsApp Cloud API
    ↓
Customer WhatsApp
```

This is **not** an automated expiry/reminder system. An admin explicitly enters the recipient and document details and clicks **Send**.

# Phase 2 — Understand WhatsApp templates

This project should use **WhatsApp message templates** for admin-triggered outbound notifications.

Your sample messages are good candidates for utility templates.

Examples:

### Insurance

Template name:

```text
vehicle_insurance_expiry
```

Body:

```text
Reminder: Insurance of your vehicle {{1}} expires on {{2}}.
Please renew before due date to comply with Section 146 of MV Act,
1988. MoRTH
```

Variables:

```text
{{1}} = vehicle number
{{2}} = expiry date
```

### PUCC

Template name:

```text
vehicle_pucc_expiry
```

Body:

```text
Kind Attention {{1}}

Pollution Under Control Certificate (PUCC) of Vehicle No. {{2}}
will expire on {{3}}.

Kindly renew the certificate before the expiry date to avoid
penal actions as per law.

Thanks. MoRTH
```

Variables:

```text
{{1}} = person name
{{2}} = vehicle number
{{3}} = expiry date
```

### Fitness

Template name:

```text
vehicle_fitness_expiry
```

Body:

```text
Kind Attention {{1}}

Fitness Certificate of Vehicle No. {{2}} will expire on {{3}}.

Kindly renew the certificate before the expiry date to avoid
penal actions as per law.

Thanks. {{4}}
```

Variables:

```text
{{1}} = person name
{{2}} = vehicle number
{{3}} = expiry date
{{4}} = authority
```

Important:

- [ ] Submit templates through WhatsApp Manager / the appropriate Business Management API.
- [ ] Wait for the template to become approved.
- [ ] Record the exact template name.
- [ ] Record the supported language/locale.
- [ ] Record the variable order.
- [ ] Record the template category.
- [ ] Test every approved template before connecting the admin panel.

Do not assume that arbitrary text generated by Python can always be sent as a business-initiated WhatsApp message.

Meta's API examples use `type = "template"` and a template name/language/components.

Reference:
https://www.postman.com/meta/whatsapp-business-platform/request/o65u5m5/send-message-template-text

# Phase 3 — Send one message manually before writing the application

Use Meta's API/Postman tooling.

Endpoint:

```text
POST https://graph.facebook.com/<VERSION>/<PHONE_NUMBER_ID>/messages
```

Headers:

```http

Content-Type: application/json
```

Example:

```json
{
  "messaging_product": "whatsapp",
  "to": "<RECIPIENT_PHONE>",
  "type": "template",
  "template": {
    "name": "vehicle_insurance_expiry",
    "language": {
      "code": "en_US"
    },
    "components": [
      {
        "type": "body",
        "parameters": [
          {
            "type": "text",
            "text": "RJ27GD5556"
          },
          {
            "type": "text",
            "text": "08-Jul-2026"
          }
        ]
      }
    ]
  }
}
```

- [ ] Send a test message to a controlled/test number.
- [ ] Confirm the message arrives.
- [ ] Confirm the template variables appear in the correct positions.
- [ ] Save the successful response.
- [ ] Record the returned WhatsApp message ID (`wamid...`).
- [ ] Test an invalid phone number and inspect the API error.
- [ ] Test an invalid template name.
- [ ] Test missing variables.

A successful send returns a WhatsApp message identifier.

# Phase 4 — Build the Python WhatsApp client

Use:

- Python 3.12+
- FastAPI
- Pydantic v2
- httpx
- pydantic-settings

Suggested structure:

```text
backend/
├── app/
│   ├── main.py
│   ├── config.py
│   │
│   ├── api/
│   │   └── message_routes.py
│   │
│   ├── schemas/
│   │   ├── message.py
│   │   └── whatsapp.py
│   │
│   ├── services/
│   │   ├── message_service.py
│   │   ├── template_service.py
│   │   └── whatsapp_service.py
│   │
│   └── templates/
│       ├── insurance.py
│       ├── pucc.py
│       └── fitness.py
│
└── tests/
```

Create a typed WhatsApp client interface:

```python
from typing import Protocol


class WhatsAppClient(Protocol):
    async def send_template(
        self,
        phone_number: str,
        template_name: str,
        language_code: str,
        parameters: list[str],
    ) -> str:
        ...
```

Then implement Meta's client using `httpx.AsyncClient`.

Requirements:

- [ ] Use HTTPS only.
- [ ] Set explicit HTTP timeouts.
- [ ] Handle non-2xx responses.
- [ ] Parse Meta's error response.
- [ ] Never log the access token.
- [ ] Do not log unnecessary personal data.
- [ ] Return the WhatsApp message ID on success.
- [ ] Use structured logging.

# Phase 5 — Build the template service

The frontend should NOT construct the WhatsApp message.

The frontend sends structured information:

```json
{
  "template": "vehicle_insurance_expiry",
  "phone_number": "+9198XXXXXXXX",
  "person_name": "Sanjay Kumar Tamboli",
  "vehicle_number": "RJ27GD5556",
  "expiry_date": "2026-07-08"
}
```

Backend:

```text
Request
  ↓
Pydantic validation
  ↓
Template-specific validation
  ↓
Template parameter mapping
  ↓
WhatsApp API request
```

Create a template registry.

Conceptually:

```python
class TemplateDefinition:
    name: str
    language_code: str
    required_fields: tuple[str, ...]
```

Do not use `dict[str, Any]` for the application domain.

Use explicit Pydantic models for each template where practical.

# Phase 6 — Build the first FastAPI endpoint

Start with one endpoint:

```text
POST /api/messages/send
```

Responsibilities:

1. Authenticate/authorize the admin.
2. Validate the request.
3. Validate the selected template.
4. Normalize the phone number.
5. Construct WhatsApp template parameters.
6. Call `WhatsAppClient`.
7. Return the WhatsApp message ID.
8. Return a safe error to the frontend if sending fails.
9. Log the internal failure details.

Example response:

```json
{
  "success": true,
  "message_id": "wamid.HBgL..."
}
```

Do not return:

- access tokens
- raw Meta authorization headers
- internal stack traces
- unnecessary personal data

# Phase 11 — Webhooks / delivery status

Once sending works, add WhatsApp webhooks.

You will eventually want:

```text
WhatsApp
   ↓
Webhook
   ↓
FastAPI
   ↓
Message status
```

Possible lifecycle:

```text
sent
 ↓
delivered
 ↓
read
```

Also handle failures.

Webhook endpoint concept:

```text
GET  /api/webhooks/whatsapp
POST /api/webhooks/whatsapp
```

GET is used for webhook verification according to the Meta setup.

POST receives events.

Requirements:

- [ ] Verify webhook requests according to Meta's requirements.
- [ ] Validate the incoming payload.
- [ ] Do not trust arbitrary webhook data.
- [ ] Make webhook processing idempotent.
- [ ] Log message IDs/statuses.
- [ ] Do not perform slow processing directly in the webhook request if unnecessary.
